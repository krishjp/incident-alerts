# Incident Notification System - Backend Worker

A Python-based automation worker that ingests live incident data feeds from **Caltrans QuickMap & Traffic CAD** to identify traffic incidents. The system filters these incidents against user-defined subscribed routes and commute time windows to send targeted SMS notifications via an asynchronous retry-enabled queue.

---

## 🌟 Key Features

* **Caltrans API Client Handler ([caltrans_client.py](file:///C:/Users/kpatel/Documents/sideRunners/incident-alerts/backend/caltrans_client.py))**: Ingests live traffic incidents directly from Caltrans QuickMap XML/KML feeds (`https://quickmap.dot.ca.gov/data/chp-only.kml`) via HTTP (< 0.1s execution time), completely replacing legacy Selenium browser scraping.
* **Asynchronous Notification Queue with DLQ ([notification_queue.py](file:///C:/Users/kpatel/Documents/sideRunners/incident-alerts/backend/notification_queue.py))**: Manages outbound Twilio SMS alert tasks asynchronously with exponential backoff retries and Dead Letter Queue (DLQ) isolation for failed dispatches.
* **$O(1)$ Bounding Box Spatial Filtering**: Filters incidents using spatial bounding boxes before calculating exact geodesic distances along turn-by-turn polyline routes.
* **AI Summary Caching**: Uses Gemini `gemini-2.5-flash` to format concise SMS notifications, cached through `cache_handler.global_incident_cache` (Redis with 24h TTL, falling back to an in-memory dict if Redis is unreachable) to avoid duplicate LLM calls for the same incident content.
* **Modern Package & Environment Management**: Fully configured via `pyproject.toml` and `uv` (`uv sync` / `uv.lock`).

## 🏗️ Backend Module Structure

* **`pyproject.toml`**: Unified project configuration file defining dependencies, dev tools, and Pytest configuration (`[tool.pytest.ini_options]`).
* **`uv.lock`**: Deterministic lockfile generated by `uv`.
* **`config.py`**: Typed, fail-fast configuration (`pydantic-settings`). Validated once at import; import `settings` from here rather than reading `os.getenv` directly.
* **`caltrans_client.py`**: The core API handler fetching and parsing Caltrans QuickMap KML feeds into structured incident records.
* **`notification_queue.py`**: Asynchronous notification queue for SMS alert delivery with exponential retry backoff and Dead Letter Queue (DLQ). Pending/DLQ tasks are mirrored to Redis so they survive a restart.
* **`redis_client.py`**: Shared Redis connection factory (supports a managed `REDIS_URL`); every caller must tolerate `None`.
* **`scrapper.py`**: Deprecated legacy wrapper module forwarding calls to `caltrans_client.py`.
* **`route_generator.py`**: Interacts with Nominatim OpenStreetMap geocoding and OSRM routing APIs to build driving polylines.
* **`route_utils.py`**: Handles polyline decoding, bounding box pre-filtering, and geodesic distance evaluation.
* **`main.py`**: Single-pass worker entrypoint — checks active PostgreSQL subscriptions, processes feeds, and manages notification queues, then exits.
* **`models.py`**: Defines SQLAlchemy models (`User`, `RouteSubscription`, `NotifiedIncident`) aligned with Prisma schema tables.
* **`fixtures/injected_incidents.kml`**: Editable sample KML feed for local testing — see [Local Testing with Injected Incidents](#-local-testing-with-injected-incidents) below.
* **`tests/`**: Pytest test suite covering API feeds, notification queue retries/DLQ/durability, route matching, config validation, and time windows.

## 🚀 Execution & Testing

1. **Environment Setup & Sync (`uv`)**:
   ```bash
   uv venv
   uv sync
   ```

2. **Run Backend Worker**:
   ```bash
   uv run python main.py                  # single pass, then exit — no long-lived loop mode
   ../scripts/run-worker-loop.sh          # repeats that on an interval (imitates Cloud Scheduler)
   ```
   Startup prints a credential-redacted config summary and aborts on invalid configuration.

3. **Run Test Suite**:
   ```bash
   uv run pytest
   uv run pytest -m "not network and not integration and not slow"   # offline only (what CI runs)
   ```

## 🧪 Local Testing with Injected Incidents

The worker never takes incidents as direct input — it always calls `caltrans_client.fetch_caltrans_incidents()`,
which fetches from a KML URL. `fetch_raw_feed()` uses `urllib.request.urlopen`, which also understands
`file://` URLs, so pointing the feed at a local fixture file is enough to fully exercise the real
`check_and_notify()` pipeline (spatial matching, dedup/update fingerprinting, Gemini summarization, the
notification queue) end-to-end without hitting the live Caltrans feed.

### Requirements

- Postgres + Redis running (`docker compose up -d`) and `backend/.env` / `frontend/.env` configured per the
  root [README](../README.md#step-2-environment-configuration).
- At least one `RouteSubscription` row in the database:
  - `isActive = true`
  - `startTime`/`endTime` window covers the current PST time (or widen it, e.g. `"00:00"`–`"23:59"`, for testing)
  - `area` matches the area your injected incident resolves to (see `AREA_PREFIXES` in `caltrans_client.py`,
    e.g. an incident number containing `LA` → `"Los Angeles"`)
  - `polyline` passes within 5 miles (the `max_miles` default in `is_within_range_pure`) of the incident's
    coordinates — easiest via the frontend UI at `http://localhost:3000`, using an origin/destination that
    geocodes near where you want the incident to land
  - a `User` with a `phone` set (phone numbers are encrypted at rest; `get_active_subscriptions()` skips
    subscriptions without a decryptable phone)

### Steps

1. Copy or edit `backend/fixtures/injected_incidents.kml` — each `<Placemark>` is one incident. Adjust:
   - the incident number in `iw-header-left` (its area-code letters drive area matching and must match a
     subscription's `area`)
   - `<coordinates>` (`lon,lat,altitude`) to fall within range of a subscribed route's polyline
   - the `iw-title`/`iw-text` blocks for the incident type, timestamp, and location text
2. Point the worker at the fixture instead of the live feed in `backend/.env`:
   ```env
   CALTRANS_FEED_URL="fixtures/injected_incidents.kml"   # relative to backend/; works in Docker too
   ```
3. Run the worker:
   ```bash
   uv run python main.py
   ```
   It does one pass and exits. On a match you should see `*** Match found for ...` in stdout, followed by a
   summarized alert; without real Twilio credentials, dispatch falls back to console-logging the SMS instead
   of sending one.
4. To exercise the dedup/update/resolved paths, edit `backend/fixtures/injected_incidents.kml` between runs
   and re-run the worker:
   - **Unchanged incident** → no re-alert. A fingerprint of the incident's `details` is stored in
     `NotifiedIncident.state`; a re-run with identical content is a no-op.
   - **Changed incident** (edit the `iw-title`/`iw-text`/timestamp text on an existing `<Placemark>`) → one
     `UPDATE` alert, because the fingerprint no longer matches the stored `state`.
   - **Resolved incident** (delete a `<Placemark>` that was previously alerted on, or rename its incident
     number) → one `Incident Resolved` alert once the incident drops out of the feed for that subscription,
     then silence — `check_and_notify()` flags it `state = "RESOLVED"` so it isn't re-sent on subsequent runs.
   A fourth case needs no feed edit: when a subscription's time window ends, its still-open incidents are
   marked stale (`state` gets a `STALE:` prefix, a log-only `STALE` message is written, no SMS). If the
   incident is still in the feed the next time the route is polled it returns to active without an SMS
   (or with an `UPDATE` if its details changed); if it's gone it stays stale.
   In all three cases, an incident is only ever re-alerted for a genuine content change or a resolution —
   never for the same unchanged, still-open incident.
5. Unset or remove `CALTRANS_FEED_URL` from `backend/.env` before running against the live feed again.

For matching logic in isolation (no DB/Redis/frontend needed), see the `MockCaltransClient` pattern in
`tests/test_caltrans_client.py`, which subclasses `CaltransAPIClient.fetch_raw_feed` directly with an in-memory
KML payload.
